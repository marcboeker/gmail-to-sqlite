# Contributing

Thank you for your interest in this project. This document explains how to
contribute. Please read it before you open an issue or a pull request.

## The short version

1. **Please start with a discussion.** It saves you time, because you get an
   answer before you write any code.
2. I read the discussion. If it is a bug or a feature I want, **I create the
   issue.**
3. **I implement it.**

That is the whole process.

## Why it works this way

This is not because I think my code is better than yours. It is a question of
time.

Agents now open issues and pull requests automatically, and in large numbers.
Many of them are low quality, and each one needs my time to review. I do this
in my free time, and that time is limited. This is not about you. It is about
the volume.

I also need to keep the project aligned with the direction I want. And I need
to focus on the core features. If every good idea is added, the project gets
bloated. A bloated project is harder to maintain, harder to use, and worse at
its main job. To prevent this, I must act as a gatekeeper. I know this is not
the usual open source model, and I am sorry if it feels strict. I think it is
the best way to keep the project healthy.

This does not mean I do not want to hear from you. **I enjoy it when you start
a discussion.** Bug reports, ideas, and questions from real people are the
best part of maintaining a project. The process only gives me one place to
read them, and it gives you a clear answer before you spend any effort.

## What to do

### I found a bug

1. Search the existing issues and discussions first. Look at closed ones too.
   The bug could already be fixed.
2. If you find an open one, do not add a comment unless you have new
   information. Use a reaction to show that you have the same problem.
3. If you find nothing, start a new discussion. Include:
   - What you did, what you expected, and what happened instead.
   - Your version, operating system, and anything else about your setup that
     could matter.
   - Logs, error messages, or a minimal way to reproduce the problem.

If I can confirm the bug, I will create an issue and fix it.

### I have an idea for a feature

1. Search the existing issues and discussions first.
2. If nobody asked for it yet, start a new discussion. Explain the problem you
   want to solve, not only the solution you have in mind.

If the feature fits the direction and the core of the project, I will create an
issue. If it does not fit, I will tell you why. A "no" is not a judgment on your
idea. It only means it does not fit here. If the feature is important to you,
you are welcome to fork the project, and I would be happy to see what you
build.

### I have a question

Start a discussion. A question is not a bug report and not a feature request.
Please do not open an issue for it.

### I already wrote the code

Start a discussion and link to your branch. Please do not open a pull request
without a discussion first.

Thank you for the effort. Once I have verified your code, I will either ask you
to open a pull request, or I will implement the change myself so the code stays
consistent. In both cases, I will credit you.

## Issues and pull requests

- **Issues are created by me.** An issue is a well-understood, actionable item.
  Everything that is not yet clear stays in a discussion.
- **Pull requests without an accepted issue:** I may not be able to review
  them.
- **Pull requests are not a place to discuss design.** Use a discussion for that.

## AI tools

Using AI tools is fine. I use them too. Before you send something, please make
sure you can explain it yourself: what your change does, and how it affects the
rest of the project.

Please write your discussion in your own words. I want to hear from you, not
from your agent.

Automated submissions are not welcome, and I may close them.

Thank you for reading this. I look forward to your discussion.
